# S1 — Foundations: a small set of ideas that stays useful

[Source guide](README.md) · [Provenance](SOURCE-MANIFEST.md) · [Start here](../START-HERE.md)

**Role:** design rationale. This is a newly written, code-free brief derived from the earlier research report and the later consolidated proposal. It is not a fresh audit of an implementation or a claim that the original report's provider advice remains current.

## The problem this source addresses

An AI system can become difficult to understand when each use case introduces another planner, profession, workflow, memory category, or special-purpose subsystem. It can also appear capable merely because it has many names, tools, and documents.

The useful foundation is smaller: continuing collaborators work in governed environments, pursue accepted needs, retain selected lessons, use permitted capabilities, and produce results whose evidence can be inspected. Different tasks can use those same concepts without becoming identical workflows.

## Six concepts and their relationships

A persona keeps an identity and perspective. An environment defines the place and boundaries of work. Work preserves the human need and accepted responsibilities. A fragment retains authored interpretation with sources and limitations. A capability provides a permitted means to observe or act. An artifact and its evidence establish what was produced and what can honestly be said about it.

A work item belongs to a governed environment. A persona may participate in several environments without carrying private context or permissions between them. A capability can be available in one setting and unavailable in another. A result belongs to an exact scope and version, not an unrestricted global pool.

Supporting records—grants, invitations, agreements, findings, and releases—connect these concepts. Their existence does not require a separate service or engine for every noun.

## Why persistent state matters

A name or conversation label does not supply continuity. Relevant identity, experience, commitments, observations, and limits must reach later decisions. Changing a model should not erase accepted work, but changed performance must still be assessed.

Memory is not a collection of unquestionable facts. Ordinary documents remain documents; fragments are authored interpretations linked to evidence. The system needs selection, correction, access control, and retention rules rather than assuming that accumulating more text creates useful learning.

## Why tools need evidence

A tool description is not proof of availability. Availability is not proof that a representative operation works. Successful execution is not proof that a result meets the task's criteria. These claims require separate evidence.

Learning a method is ordinary work. A curriculum can be represented as work in an environment; no special mechanism should award competence merely for completing a lesson count. Domain review must be available in actual work when the claim needs it, not only in a hidden evaluation campaign.

## What this means for a reader or builder

Start with one useful continuing collaborator. Keep its purpose, permissions, actual results, and unresolved conditions visible. Add cooperation or new identities only when the work and evidence justify them. An understandable interface should answer what is wanted, what is happening, who accepted responsibility, what changed, and what needs a human decision.
