# Provider integration

Providers expose model discovery and a decision call. `ModelRequest` carries the persona identity and character, chosen model and effort, work and environment, selected document versions, document metadata, relevant messages, tool metadata and active action history. It also states the ordinary action interface. A decision contains a concise summary and actions with JSON arguments. Results are persisted and reach subsequent decisions through the same loop.

The Codex adapter uses the installed app-server protocol. It initializes an experimental client, discovers the paginated `model/list`, creates a thread with explicit application instructions, and requests a structured decision. The adapter uses the exact requested model without provider fallback. It records the model in the returned thread configuration and token usage notifications. Host effects are requested through the application's action interface; native provider command tools are disabled for this adapter so effects can be recorded by the host job engine. This does not restrict which host commands that engine can run.

The adapter retains the provider's errors and raw event stream. A provider interruption does not imply zero usage. Model availability and capabilities are provider facts, not an application ranking. This integration follows the [official app-server thread interface](https://learn.chatgpt.com/docs/app-server#start-or-resume-a-thread) and validates it against schemas generated by the installed executable.

Additional providers are JSON executable bridges configured as a mapping from provider names to argv arrays. `--models` returns model metadata. A normal invocation reads a `ModelRequest` on stdin and returns `ModelResponse` on stdout. Standard error and the returned bytes are retained. The bridge may use any provider API or third-party library the host supports; the persona identity and learning remain application records.

Application accounting includes only what its adapters and host action engine observe. It cannot count every model request issued by arbitrary other programs on the shared host. Provider capabilities, operating-system permissions and explicit user instructions govern execution.

Codex decisions use a closed per-operation structured output schema. Optional fields are nullable on the provider wire and omitted before dispatch. Command text and retained documents are ordinary string fields inside argument objects. `attributes_json` is a provider-wire field for arbitrary character extensions; the adapter validates and converts it into `attributes`. External bridges return `DecisionAction.args` as ordinary JSON objects. The runtime retains malformed actions as failures without executing them. The schema follows OpenAI’s [structured output requirements](https://developers.openai.com/api/docs/guides/structured-outputs/), including closed object properties and nullable optional fields.

On the Codex wire, an action is `{kind, parameters}` so constrained generation chooses its operation before generating the corresponding parameter shape. The adapter maps `parameters` to the provider-neutral `args` object; raw provider output and the exact output schema remain in call files. JSON property order is preserved. Action replay identity compares semantic request values, independent of object-key ordering.

An empty in-memory catalog is discovered when persona creation, model choice or resumed work needs it. API clients do not need to open the model-list view first. Failed requests preserve the requested model, provider error and any reported usage; capacity errors do not silently substitute another model.
